# test stream — build spec

Source of truth for product decisions is `overview.md`. If they conflict, follow the human file. This file is the implementable version of that plan, and it describes what is in the repo now. The chat has its own document, `chat.md`.

## goal

Run one program set on one machine. A person opens `https://<that-machine-ip>` and either goes live from the browser or watches someone who is live.

One streamer per stream. Many watchers. The streamer uploads once. The machine copies packets to each watcher. No transcode. Accounts are optional (see "accounts").

This is a lab. It is reachable by anyone who can hit the IP. That is accepted.

## non-goals

Do not build these.

- stream keys, permission roles, email, password reset, oauth, 2fa (accounts are a name and a password, optional: see "accounts")
- follows, vod, recording, moderation (the text chat is in: `chat.md`)
- transcoding, simulcast, quality ladder, cdn
- group calls where several people publish into one room
- a second machine, a real fanout tier, TURN, ICE-TCP
- mobile apps, OBS ingest, RTMP

Leaving them out is the point of the test. Structure the media path so a later fanout machine can be added without rewriting the site.

## how a session works

```mermaid
flowchart LR
  cam[browser camera] --> enc[browser compresses]
  enc --> ingest[ingest on this machine]
  ingest --> fan[fanout on this machine]
  fan --> w1[watcher browser]
  fan --> w2[watcher browser]
```

1. Streamer opens `/live`, types a name, allows the camera, hits start.
2. The page calls go-live. The api opens a `sessions` row, sets the redis key, and returns the socket path plus a session id and a random token. Heartbeat and stop must carry both.
3. The browser compresses camera and mic locally, then opens one WebRTC connection to `video` and publishes.
4. The name shows up on home.
5. A watcher opens `/watch/:name`. The page asks the api, then opens its own WebRTC connection to `video`, which copies the streamer's packets to that watcher. It does not decode them.
6. More watchers mean more copies out of the same machine. The streamer still has one upload.
7. Streamer hits stop, or closes the tab. Watchers get `{"event":"ended"}` and are closed. The name leaves home at once.

Reject a second publisher on a name that already has one. First streamer keeps it until stop, tab close, or the connection fails.

One quality. Every watcher gets whatever the streamer is sending.

## processes

One machine. Ten services in `docker-compose.yml`; `certs` and `pages` run once and exit; `dummy` idles unless `DUMMY_STREAMS` is set. Every long-running one logs to json-file capped at 3 × 10 MB (the `x-logging` anchor), so a box left alone does not fill its disk with caddy's access log.

```mermaid
flowchart TB
  certs -.->|cert volume| frontend
  pages -.->|pages volume| frontend
  browser[browser] -->|https :443| frontend
  frontend -->|/api| api
  frontend -->|/ws| video
  api --> database
  api --> redis
  api --> s3
  api -.->|GET /live| video
  video -.->|is this session open · attached| api
  browser -->|media udp :7882| video
  dummy -->|ws + media, like a browser| video
  dummy -.->|bio, go-live, heartbeat| api
  frontend -->|/chat/name| chat
  chat --> redis
  chat -.->|is this the streamer| database
  dummy -.->|pretend viewers| chat
  frontend -->|/events| events
  api -.->|XADD live, ended, viewers, status| redis
  redis -.->|the events stream, tailed| events
  events -.->|who is this cookie, the choice| database
  frontend -->|"/api/streams"| home
  redis -.->|the events stream, tailed| home
  home -.->|GET /viewers at boot and every 30s| video

```

The frontend never touches video packets. The api serves one html route, `/watch/<name>`, and it is the pages' own `index.html` with a different head; it never builds pages of its own. `video` never serves pages.

`video` speaks one websocket on `:7880/ws` (not published; reached through the frontend). The browser sends a single JSON text frame to set up, then keeps the socket open until it hangs up.

```json
{"role":"publish","name":"billy","sdp":"<offer sdp>","session":12,"token":5551212}
{"role":"watch","name":"billy","sdp":"<offer sdp>"}
```

The server answers `{"sdp":"<answer sdp>"}`. `"error"` instead of `"sdp"` means no: `"someone is already live"`, `"not live"`, `"not your stream"`, `"api unreachable"`, `"bad name…"`, `"bad offer"` (over 48 KB, over 6 `m=` lines of any kind, unparseable, a publish offer that sends on nothing or has a section without a mid, a watch offer that receives on nothing), `"could not negotiate"`, `"server error"`. The browser has 10s to send its frame and the server 10s to answer. When the publisher leaves, watchers get `{"event":"ended"}` and the socket closes. A watch frame may carry `"preview":true` (home's muted camera previews): a preview gets the same answer and events but is not counted as a viewer and spends none of the per-address watcher caps (`viewers.md`); one address holds at most 12 previews in all, past which it gets `"too many previews from your address"`.

**Slots.** A publisher's offer can carry several video sections: the camera, and empty `sendonly` ones for screens it may share later (the pages offer `1 + SCREEN_SLOTS` = 4). Every audio/video section it sends on is a *slot* of the room, in offer order, each with its own outgoing track (`TrackLocalStaticRTP`, id `<kind>-<mid>`), all made when the room is claimed. A watcher's offer says how many audio and video sections it can receive on, and the slots are bound to them in order, as many as fit: a watcher asking for one video gets the camera; one asking for four gets the camera and the three screen slots, bound before anything has been sent on them. So a screen the streamer shares mid-stream (`replaceTrack` into an empty section) reaches everyone already watching without a renegotiation anywhere: its packets are routed to the slot by mid when they start. Packets alone do not say what is live (an empty section still gets padding, a muted track never says so), so the publisher says: later frames on its socket, `{"slots":[{"slot":0,"kind":"camera"},{"slot":1,"kind":"screen","label":"screen"}],"scene":{"layers":[{"id":"s1","kind":"screen","slot":1,"x":0,"y":0,"w":1,"h":1},{"id":"cam","kind":"camera","slot":0,"x":0.73,"y":0.714,"w":0.25,"h":0.25}]}}`, the video slots live right now (`slot` counts its video sections from 0; `kind` up to 16 bytes, `label` up to 64, one entry per slot at most, else the frame is ignored and logged) and, optional, how its frame is laid out (`scene`, `screen.md`: layers bottom first, at most 16, each an `id` of 1 to 16 plain characters, a `kind` of `camera`, `screen` (with a `slot` of that offer) or `image` (with an `asset` id), an optional `fit` of `cover` or `contain`, and `x`, `y`, `w`, `h` fractions of a 16:9 frame in 0..1; anything else and the frame is ignored and logged). Watchers get it as `{"event":"slots","slots":[...],"scene":{...}}` right after their answer and on every change, the scene passed on as it came; until the publisher has said anything, the first video slot is `camera` and there is no scene (which is all the dummy, or an older page, ever has). A new watcher gets one keyframe request per picture on connect; further watcher PLI/FIR are forwarded to the slot they are about at most once per 1.5s per slot, and no two requests for one slot go out within 300ms, so a burst of joins shares one keyframe. Header extensions from the publisher are stripped before fan-out. Lost packets are re-sent to watchers from a 512-packet history. ICE calls a vanished peer disconnected after 5s and gives up at 20s. On SIGTERM every room ends, every watcher gets `ended`, and the process exits as soon as those frames are out (2s at most; axum stops tracking a socket once it is upgraded, so `video` waits for its own tasks).

`video` also serves `GET /thumb/<name>.jpg` (caddy routes `/thumb/*` to it): the latest picture of a live stream, `Cache-Control: private, max-age=3`, 404 for anything not live, and 404 too while the newest picture is older than 6 × `THUMB_EVERY_SECS` (the video stopped coming while the connection held, or ffmpeg died: a frozen frame is not served as live). It is made on this machine for every publisher, browser or dummy: when a publisher's video track comes up, a small ffmpeg is started beside it (`video/src/thumbs.rs`), fed a copy of the VP8 packets over localhost as plain RTP described by an SDP file in `/tmp`, and writes a 320px jpeg atomically to `/tmp/thumb-<name>.jpg`, the first decoded frame right away and then one every `THUMB_EVERY_SECS` (5). Browsers only send a keyframe when asked, and ffmpeg's VP8 depacketizer drops every frame after a lost one until a keyframe comes, so `video` requests one every 2s whenever the picture is missing or older than 2 × `THUMB_EVERY_SECS`, for as long as that ffmpeg lives (quiet while the pictures come; a lost packet the sfu got back by nack arrives late, and ffmpeg is told to wait 500ms for one, `-max_delay`, before calling it lost); the first picture shows up a second or two after going live. ffmpeg found dead is logged once and its last picture taken down; at start, files an earlier run left behind are removed. It decodes every frame, roughly 5–10% of a core per 720p stream, so viewers pay nothing (decoding only keyframes would mean asking the publisher for one every few seconds, and every viewer would download those). `THUMBS=0` turns it off; a `video` image without ffmpeg just logs that and serves 404. Nothing is stored anywhere; the file goes with the room.

A publish frame must carry the `session` and `token` that go-live handed out. `video` asks the api (`POST {API_URL}/api/streams/<name>/heartbeat?session=&token=`, 1.5s timeout) whether that session is open for that name: 200 → go on, 4xx → `{"error":"not your stream"}`, no answer → `{"error":"api unreachable"}`; a frame without them is `not your stream` too. The check comes after the cheap ones (name, offer), so a bad offer is still `bad offer`. This is what makes "only your login can go live as it" hold on the socket and not just at go-live: whoever skips the api has no session. Names starting with `DUMMY_PREFIX` (`dummy-`) are reserved for the fake streams as well and need `"password": "<DUMMY_PASSWORD>"` in the frame, else `{"error":"reserved name"}`. With no `DUMMY_PASSWORD` set they are refused outright. The api applies the same rule to go-live (`?password=`, 403 otherwise). `video` does not read redis or the database. It exposes `GET /live` (sorted JSON array of names connected right now) and `GET /health` (`ok`).

## fake streams

`video dummy` (`video/src/dummy.rs`) runs one ffmpeg per stream: one lavfi input with the one `-re` (`color` 480×270 @ 15 fps; `sine` at a per-stream pitch, `volume=0.15`), the stream's gifs as inputs of their own (`-stream_loop -1`, no `-re`: the overlay takes their frames as the paced frame needs them), and a `-filter_complex` that `scale`s each gif to its height and `overlay`s it with `x`/`y` = `abs(mod(t·v + phase, 2·(W−w)) − (W−w))`, the dvd-logo triangle wave, evaluated per frame with `t` the time (`drawbox`, which the box used to be, evaluates its expressions once and its `t` is the thickness: the box never moved), then `drawtext` name and `%{pts}` clock as `HH:MM:SS`, each on a dark box; libvpx (`-deadline realtime -cpu-used 8`, 500 kbps, 2 s GOP) and libopus to RTP on two localhost ports; the Rust side `write_rtp`s those packets into two `TrackLocalStaticRTP`s on a peer connection that did the normal `/ws` publish handshake: go-live at the api first (`?password=`), then the frame with that `session` and `token` plus `"password"`. The deck is every `.gif` in `DUMMY_GIFS` (`/usr/share/dummy-gifs`), shuffled once per start (xorshift, no crate); stream `i` is dealt the three after stream `i−1`'s, round and round, and each starts in its own corner (top left, bottom right, top right, bottom left, in turn) at its own speed and height (120, 90, 104), so no two streams look alike. The image shrinks `random-media/gifs` to 144px / 15 fps with a palette of their own at build time (`Dockerfile.dummy`, a stage of its own, so only the 3 MB of small ones ship, not the 24 MB of originals): decoding three originals (up to 640px at 50 fps) cost more than encoding the stream. No gifs on the machine → a warning and the coloured box bounces instead. `-threads 1 -filter_threads 1 -filter_complex_threads 1` sit after the `-i`s: before them they only limit the source, libvpx spins one thread per core, and every `scale`/`overlay` gets a pool of one thread per core (measured: ~100% → ~8% per stream for the box; the three small gifs add a few percent). `DUMMY_STREAMS=0`, an empty password or an empty `API_URL` → the container logs why and idles. `DUMMY_NAMES` entries that break the name rule are skipped with a warning (that rule is also what keeps them safe inside the `drawtext` expression). A pretend chatter whose nick has since been claimed by a signup is refused by the chat; the dummy logs that once and that chatter stays quiet. The pages show a `test` badge on `dummy-` names.

What each store holds:

- **database** — `streamers`: `name`, `bio`, `avatar`, `avatar_at`, `updated_at`, plus `password_hash` and `created_at` once the name has an account; `logins`: the hashed login tokens (see "accounts"). `avatar_at` is when the profile picture was saved (the `?v=` of its url); the jpeg itself is in the bucket. `avatar` is only a picture saved before that, and is cleared the next time it is read. `offline_at` is the same for the offline picture (the one the watch page shows where the player would be while the name is not live), and `offline_note` the line under the word there, '' for none. `stream_thumbs`: one row per picture on the home card (`name`, `id`, `created_at`), at most 6, oldest first. the jpeg is in the bucket; `id` is 53 bits from the os rng, so it survives a js number. `stream_assets`: one row per picture of the scene (`screen.md`: `name`, `id`, `mime`, `bytes`, `created_at`), at most 24, the same id and the same name key, renamed with the thumbnails; the bytes are in the bucket. `sessions`: one row per go-live with a random `token` (53 bits from the api's os rng, so it survives a js number) and `verified` (the go-live came from the name's own login), `ended_at` null while live. A row whose tab vanished without stop is ended by a sweeper once a minute, starting a minute after boot: open, older than 3 minutes, no live key holds its id, and `video` does not list its name as connected (a key can lapse under a live stream when the api was down past the ttl or redis restarted; the page's next heartbeat takes it back). When `video` does not answer, nothing is ended that round. Survives a restart. No vod. A bio can exist while they are offline.
- **redis** — `live:<name>` = session id, `SET NX EX 90`. Heartbeat refreshes every 15s; `stop` deletes. It is a lock, not the truth: when `video` answers, the api uses `video`'s connected list for home and for `watch.live`, treats a key with no connected publisher as stale once its session is older than 20s (deleted on the next go-live, only if it still holds that id; younger, the publisher is still on its way to `video` and the name is taken), and refuses a go-live when `video` says the name is connected even if the key is gone. When `video` does not answer, redis alone decides, and go-live refuses (503) rather than guess.
- **s3** — the bucket named by `S3_BUCKET` (default `stream`) on the seaweedfs container, while `S3_ENDPOINT` is `off`. profile pictures are `avatars/<id>.jpg`, stream thumbnails are `thumbs/<id>/<n>.jpg`, offline pictures are `offline/<id>.jpg` and the scene's pictures `assets/<id>/<n>.<ext>` (the row's uuid, `ids.md`). survives a restart (the `s3-data` volume). a url in `S3_ENDPOINT` means the api is not using this container.

## browser https rule

`getUserMedia` only runs in a secure context. `http://<ip>` redirects to https. Serve the site on https with a self-signed cert. The browser warning is expected. After the user proceeds, the camera works.

WebRTC signaling from the page must use `wss` to the same host, proxied to `video` at `/ws`. Otherwise a https page will refuse a `ws` socket. The api returns `url: "/ws"`; the page builds `wss://<location.host>/ws`.

## deploy

`./scripts/deploy.sh` on the machine. It picks `PUBLIC_IP`, writes `.env`, builds the pages and the three Rust images (`api`, `video`, `dummy`) one at a time, runs Docker Compose, and waits for `/api/health`. From another device on the same network, or from the public internet if the ports are open, browse to the machine IP.

```text
https://<PUBLIC_IP>/
```

`PUBLIC_IP` is the address browsers and WebRTC should use. LAN test: the LAN IP. VPS test: the public IP. Cloud VMs with a private NIC and a mapped public IP: the public one.

Ports that must be reachable:

| port | proto | use |
|---|---|---|
| 80 | tcp | redirect to https |
| 443 | tcp | pages, `/api`, `/ws` |
| 7882 | udp | all media, one port (udp mux) |

`7880/tcp` is not published. `video` must advertise `PUBLIC_IP`, not a docker bridge address. If it advertises the wrong IP, the socket connects and the video stays black.

No STUN, TURN, or ICE-TCP. Watchers who cannot reach udp 7882 get no video. Same LAN, or a VPS with that port open, is the supported setup.

The database volume keeps bios, accounts and sessions. The s3 volume keeps the bucket. Redis does not use a volume, so a restart of that container clears "who is live", "who is here" (the `seen:` sets; the gateway puts them back from its open sockets within 30s), the `events` stream, every room's chat history and the login/signup/error-report counters. The cert is a named volume written by `certs`; nothing in the repo.

## config

`.env` holds the values that change per machine: `PUBLIC_IP` and `CARGO_BUILD_JOBS` (`deploy.sh` writes both and keeps every other line), `ENV_NAME` (what the box calls itself in `/api/health` and every stored error; empty, and `deploy.sh` writes the machine's hostname in once, never touching a set value; still empty by hand = `unnamed`), `ADMIN_NAMES` (accounts that may read `/api/errors` and open `/admin`; each needs an account on that box or the api drops it at boot with an error line), `OPS_TOKEN` (a machine's bearer token for `/api/errors`; 16 characters at least, shorter is ignored with a warn line), plus the optional fake-stream settings `DUMMY_STREAMS` (default 0), `DUMMY_PASSWORD` (empty = reserved names refused), `DUMMY_NAMES` (comma list; default `dummy-mango, dummy-pixel, dummy-disco, …`), and the bucket: `S3_ENDPOINT` (`off` = the seaweedfs container; a url = that bucket), `S3_BUCKET` (default `stream`), `S3_REGION` (default `us-east-1`), `S3_ACCESS_KEY`, `S3_SECRET_KEY` (both required once `S3_ENDPOINT` is a url; ignored while it is `off`), `S3_PATH_STYLE` (empty = path-style, except `*.amazonaws.com`). Database, redis and the container bucket's passwords in this test are the literals in `docker-compose.yml` (`stream` / no redis password / seaweedfs `stream` / `stream-s3`).

The api container receives:

```text
DATABASE_URL=postgres://stream:stream@database:5432/stream
DEBUG_DATABASE_URL=postgres://stream:stream@database:5432/debug
REDIS_URL=redis://redis:6379/0
VIDEO_URL=http://video:7880
PORT=4000
ENV_NAME=<hostname>      ADMIN_NAMES=            OPS_TOKEN=          (from .env, see debugging.md)
S3_ENDPOINT=off          S3_BUCKET=stream        S3_REGION=us-east-1
S3_ACCESS_KEY=           S3_SECRET_KEY=          S3_PATH_STYLE=
```

The video container receives `PUBLIC_IP` (must be an ipv4 address, or it refuses to start: anything else would fail every negotiation while `/health` says ok), `WS_PORT=7880`, `UDP_PORT=7882`, `API_URL=http://api:4000` (where it checks publishers' sessions), `DUMMY_PASSWORD`, `THUMB_EVERY_SECS=5` (and optionally `THUMBS=0`), `RUST_LOG=warn,video=info,webrtc_ice=error`. The api also gets `DUMMY_PASSWORD`. The dummy container gets `DUMMY_STREAMS`, `DUMMY_PASSWORD`, `DUMMY_NAMES`, `VIDEO_WS_URL=ws://video:7880/ws`, `API_URL=http://api:4000`.

`BUILD` is a build arg, not `.env`: `deploy.sh`, `ship.sh` and the action set it to the commit the images are named after — the last one that touched what they are built from, the pathspecs in `image-paths` (`api/ video/ frontend/` minus the Caddyfile, `Cargo.*`, `.dockerignore`, the workflow), 7 characters, `-dirty` when those have edits or new files — and the `pages`, `api`, `video` and `dummy` images bake it in (`ENV BUILD`, vite `define` `__BUILD__`); it goes on the `compose build` command line as well as in the environment, so a `sudo docker` fallback cannot lose it. A hand-run `docker compose build` gets `dev`; `BUILD=$(git rev-parse --short HEAD) docker compose up -d --build` is the by-hand equivalent (HEAD is close enough by hand). `/api/health` and every error report carry it, and from the scripts and the action it is the image tag. Because the image carries it, a commit that touches an image path is a new image for every service, cache or not; one that touches none is not: see "deploy script".

There is no video api key. The test does not check one.

Hostnames on the compose network are the service names: `frontend`, `api`, `chat`, `database`, `redis`, `video`, `dummy` (`certs` and `pages` exit before anyone could call them).

Errors are `{ "error" }`; unknown routes 404 `no such route`; bad JSON 400 `bad json body`; a missing or malformed query string (`stop` without `session`) 400 `bad query string`. `PUT` bio trims and caps at 500 chars. `video` is asked over http with a 1.5s timeout.

### the watch document

`GET /watch/<name>` (and `/watch/<name>/`) is html, the api's only one. Caddy sends `/watch/*` to the api instead of the files. It exists for link previews: iMessage, Discord, Slack and X make the card with a bot that fetches the url once, reads `<title>` and the `og:*` tags, and never runs js, and the spa's `index.html` says "streams" for every page.

The api reads `index.html` from the `pages-data` volume (mounted read-only at `/srv`, `PAGES_DIR`) on every request, so the hashed asset names are always the current build's and `./scripts/deploy.sh frontend` needs no api restart. It drops the `<title>`, and before `</head>` adds: `<title>name · live|offline</title>`, `description`, `canonical`, `og:type website`, `og:site_name streams`, `og:title`, `og:description` (the bio as one line, 200 chars, or `live now` / `not live right now`), `og:url` (`https://<host>/watch/<name>`, from the `Host` header caddy passes through, never the query string), `twitter:card`, `twitter:title`, `twitter:description`, and when there is a picture `og:image` + `twitter:image`. The picture is the stream's thumbnail (`/thumb/<name>.jpg`, checked with a `HEAD` to `video`, so a stream younger than ~6s has none) with `summary_large_image` while live, else the offline picture (`/api/streamers/<name>/offline?v=`) with `summary_large_image` while not live and they set one, else the profile picture with `summary`, else nothing. Live without a thumbnail yet is the profile picture, not the offline one: that picture is for a page with no player on it.

The body is the same `<div id="root">` and `<script>`, so react boots and the watch page runs exactly as from caddy. Inside `#root` goes the profile card from `index.html`'s `<template id="watch-shell">` with `{{avatar}} {{banner}} {{name}} {{verified}} {{status}} {{tone}} {{bio}}` filled in (html-escaped), so the name, picture, status and bio are on screen before the js has loaded; `createRoot().render()` replaces it. `{{banner}}` sits in the `style` attribute of the player's black box and becomes `background-image:url(…)` of the offline picture when the card is that, else nothing: a style, not markup, so pages newer than the api show a black box and not the placeholder's words. The card uses no test ids. `Cache-Control: no-cache`, like `index.html`.

An invalid name or an extra path segment gets the untouched `index.html` with a 404, so the spa shows its own "bad name" / not found. If the volume has no `index.html` yet: 503 `pages not published yet`.

Previews are cached by the chat apps (Discord for hours, X for days, iMessage on the sender's device), so the status in a card is the status at first unfurl. The watch link the live page hands out is therefore `/watch/<name>?s=<session>`: a new url every time you go live, a fresh card every time. The page and the api ignore `?s`. Previews need a certificate the bots trust; with the self-signed one they fetch nothing.

### accounts

Optional. Without one you are whatever name you type, like before. With one, the name is yours: only your login can go live as it, save its bio, or talk as it in chat (an anonymous nick equal to a claimed name is refused). Home and watch show a `✓` on a live stream its account started (the session's flag, not the name's: signing up as a name somebody is streaming under anonymously does not decorate their stream), chat lines said by a login carry `verified`. See `accounts.md` for the why.

- password: normalised (nfkc), then 8 to 128 characters, the same rule at signup, login and change. argon2id (19 MiB, 2 passes, 1 lane) in `spawn_blocking`, at most 4 at a time. the stored string carries salt and settings. the api never logs request bodies.
- login: 32 random bytes, hex, in `login=<token>; Path=/; Max-Age=2592000; HttpOnly; Secure; SameSite=Lax`. the `logins` table keeps `sha256(token)`, `name`, `expires_at` (30 days, fixed), `last_seen` (moved at most once an hour). a new login does not end the old ones (many devices); a name's expired rows are swept when it logs in. `Secure` still sets on `http://localhost` (chrome, firefox), so `npm run dev` works. `SameSite=Lax` is the csrf story: another site's form cannot post with the cookie; `logout`, which needs no cookie, checks `Sec-Fetch-Site` as well.
- which names have an account is public: `verified` on `GET /api/streamers/:name`, the lists and watch, the `✓`, and chat's refusal of an anonymous nick on a claimed name all say so. the login error hides which of name and password was wrong, nothing more.
- the cookie goes with the `/chat/:name` and `/events` handshakes too; that is how chat and the gateway know you (from inside the events worker as well: same origin).
- a login can join groups (`groups.md`): each puts a badge next to its name in chat. `bot` is built in and automatic; the chat's `hide bots` puts those lines away.
- no email, so no reset: `./scripts/deploy.sh passwd <name>` (= `docker compose exec api api passwd <name>`) prints a new random password once and logs every login of that name out. on a name with no account it makes one.
- no new secrets. nothing to rotate.
- `video` holds the same gate on the socket: a publish frame carries the go-live `session` and `token`, and `video` asks the api that they are open for that name before it takes the stream (see the ws protocol above). The api decides who may go live; `video` only checks that it did.

Home does not poll. One `GET /api/streams` when the page arrives (the home service's snapshot, `home.rs`, first on first: the order is the service's, and so will the ranking be when there is one), then the facts over the events socket under `watch *` (`status.md`): `live` puts a card at the end with what the fact carries (bio, ✓, picture, `thumbs`; `viewers` null until video has counted), `ended` takes it out, `viewers` moves the chip. Frames that land while the snapshot is in flight are held and applied on top of it. The snapshot is asked again when the events socket opens or comes back under the page (the facts of a gap are gone; one in flight as it opened is followed by another), and after an ask that failed, 3s doubling to 60s. A 1s tick is the page's clock for the chips. Leaving keeps the list, so coming back shows it at once while it is asked again. The video websocket is only for the camera. The events websocket (`/events`, `status.md`) is open on every page, one per browser in a shared worker (a socket per tab where there is none), and carries presence and the pushes; a handshake that never opens backs off from 3s to 60s with jitter, a socket that was open and dropped is back in 3s. Three grey placeholder cards (`#loading`) until the first answer; when the api stops answering, `api is down: …` alone (the last list is not kept on screen). The cards live in `#list article` and each thumbnail is `img[data-thumb=<name>]`; the tests key on those. The first two are `#featured` (`data-featured=<name>`): they play the camera for as long as the page is open and visible, muted, over their still, which shows until the camera is playing (a hidden tab holds no previews; they start again when it shows). Every other card shows one picture for the whole visit, chosen when it first appears: one of `thumbs` when the streamer put some, otherwise one camera frame (`/thumb/<name>.jpg`). A refresh can land on a different one. A 404 (the first camera frame takes ~6s) asks again a few times and then stops; once a picture has loaded, the url does not change. Holding the pointer on a card for 300ms (or focusing it) plays that same camera over the still, muted, and leaving hangs it up. A pass across the grid and a tap do not. The camera is the 720 picture the streamer sends; there is no second encode.

The controls are the same (`#pip-chat`, `#pip-popout` lit and named "back to the page", `#pip-close`, the sound chip, the stats; the same ids, in the window's document); the chat opens in the window where the setting says, and the window grows by the chat first where the browser lets it (`resizeBy`), the picture making room otherwise. The window goes with the box: pop out again (or the window's own ×) brings the box back into the page where it was left, the stream's own page (a click on the picture or the name there) closes it as it hides the box, `×` ends the stream and closes it, and a page load or a closed tab closes it with the page. The player is only the watch session seen from outside the page: the same atoms, the peer connection and socket kept as module handles, so nothing is copied or reconnected. A stream that is not live yet can wait in the corner too ("not live yet. checking"). The box itself (`CornerPlayer`: the drag, the resize, the fit, the chat places, the pop out) is shared with the broadcast's player (`#live-pip-player`, under "Go live"); both sit at the bottom right (`#corner-players`) until dragged

Use the browser `RTCPeerConnection` directly, no iceServers. `<video>` elements autoplay, playsinline, muted on the streamer's own preview and on every tile so they do not hear themselves, or twice. The watcher offer has four recvonly video transceivers (the camera and the screen slots) and one recvonly audio transceiver.

## frontend

Same stack and conventions as Axiom-Frontend, scaled down: Vite 8 + React 19 + TypeScript (strict) + Tailwind 3 with the same token names (`background`, `textPrimary`, `primaryBlue`, `primaryStroke`, `increase`, `decrease`…) fed by css variables, Jotai 2 atoms, React Router 7, TanStack Query for the home poll, `clsx` + `tailwind-merge`, Geist, oxlint + oxfmt (`printWidth` 169, single quotes, no trailing commas).

The look: hard edges. The tailwind theme has no border radius at all (`borderRadius: { none }`, so a `rounded-xl` typed out of habit produces no css), every box is a 1px stroke on the secondary background with a solid offset shadow (`shadow-hard`; `shadow-hard-blue` on hover and focus for boxes that are links, `shadow-hard-lg` for the corner player), buttons move onto their shadow when pressed, inputs turn their border blue on focus instead of a ring, avatars and the live dots are squares, page titles carry a 4px blue bar on the left and the header a rule underneath. `panelClassName()` in `shared-components/Panel.tsx` is the one place the box look lives. The api's pre-react watch card (`api/src/profile.rs`, `index.html`'s template) follows the same rules by hand, in the same token classes, so it takes the theme too; the monitor's page (`api/src/monitor.html`) copies the dark values by hand and stays dark (another box, another origin).

Conventions kept from `frontend-conventions.mdc`:

- Session state lives in atoms (`src/infra/atoms/publish-atoms.ts`, `watch-atoms.ts`, `presence-atoms.ts`); the peer connection, sockets, the events worker's port, the inspector's ring and timers are module handles because nothing renders from them.
- Every transition is a wrapper action function (`goLive`, `stopLive`, `watch`, `retry`, `markPlaying`…). No `useEffect` that reacts to state. The only effects are mount-only: open the camera, start watching, and the cleanup that ends the stream when the route unmounts (unless picture in picture keeps it). The `pagehide` listener that ends a broadcast on tab close belongs to the stream (`goLive` adds it, `stopLive` removes it), because the stream can outlive its page.
- `store` is the file-level `getDefaultStore()` in `src/infra/store.ts`. `VideoFrame` binds `srcObject` through `store.sub` on a MediaStream atom, not through a reactive effect.
- Element ids and status strings are stable (`#name #start #stop #status #video #unmute #volume #stats #stats-panel #live-stats #live-stats-panel #tap-to-play #retry #pip #presence #my-presence`, "live", "watching", "ended…") because the browser tests key on them. `status` means the stream's status line everywhere; everything about who is around says `presence`.

## deploy script

`scripts/deploy.sh`, run from the repo root. Four modes and three flags; `--help` lists them (bold on a terminal, plain when piped). By default nothing is compiled: every mode gets the four images from a registry (the one the git remote implies, `ghcr.io/<owner>/`, or `IMAGES` in `.env`/the environment) at the tag of the last commit that touched what they are built from (`image-paths`); `--build` compiles them on the machine instead, `--images TAG` names a different tag:

- `./scripts/deploy.sh [PUBLIC_IP]` — full deploy, described below. First time on a machine, or whenever the ip changes.
- `./scripts/deploy.sh frontend|api|video|dummy …` — partial. Keeps `PUBLIC_IP` from `.env`, rebuilds only the named images, swaps only their containers (`compose up -d --no-deps`), then checks what it swapped — the container is `running` with no restart since the swap and, where the image has a healthcheck (`api`, `chat`, `events`, `home`, `video`), `healthy` within 60s; `/api/health` alone would not do, it says 200 with `video` down — removes the untagged images the swap left behind (`docker image prune -f`: dangling only, never volumes or the build cache), and then waits for `/api/health`. A container that is not up fails the run with its last 30 log lines; there is no rollback (the old image lost its tag), the way back is a fix and another deploy. Like a full run it checks free disk and adds the swapfile first (swap is session-only, so the first partial after a reboot would otherwise build without it). `frontend` rebuilds `pages` and re-runs the copy, and the one-shot's exit code is the verdict (a full disk fails the run); caddy is not restarted, so live websockets survive. `api` is a few seconds of 502 on `/api`; streams survive (heartbeats ignore non-4xx failures); the `api` redeploy also creates the `s3` container when it is missing (the api waits for the bucket at boot; an existing one is left alone, `--no-recreate`). `video` ends every live stream and prints a warning first. `dummy` rebuilds the fake-stream image and applies the `DUMMY_*` values from `.env`; `video` and `api` read `DUMMY_PASSWORD` too, so they are recreated when it changed (with `--build` compose sees that by itself; in images mode the running `video`'s value is compared with `.env` first, because their wanted image is this run's tag and an `up` that includes them would also swap them for a tag that moved, `video` with every live stream). An ip argument with services is refused: an ip change is a full deploy.
- `./scripts/deploy.sh --pull [services…]` — `git pull --ff-only` first (needs an upstream; refuses otherwise). With no services named, the files changed since the last deploy pick the services: `api/**` → api, `video/**` → video + dummy, `Cargo.toml`/`Cargo.lock` and the root `.dockerignore` → api + video + dummy, `frontend/Caddyfile` → caddy reload in place, other `frontend/**` (its `.dockerignore` included) → frontend, `docker-compose.yml` → `compose up -d`. They run in that order — pages and images first, `compose up -d` last — so the plain `up` starts the new images rather than the old ones. Docs, tests, `monitor/`, `.env.example` and `scripts/` map to nothing. "Since the last deploy" is `.deployed` (gitignored), written with the commit at the end of every full or partial run that ended well, when it is an ancestor of HEAD; else the pre-pull HEAD. So a `--pull` that died in a build leaves `.deployed` where it was, and the next `--pull` — even with nothing new upstream — says so and redeploys what the failed one did not, instead of "nothing changed". A pull that moves HEAD without touching a service file says which commits it skipped, lands new `.env` keys, and advances `.deployed`. When the pull changed `scripts/deploy.sh`, the running script hands over to the new one (`exec`, same arguments, the pre-pull head passed along) before deciding anything; its last line is `main "$@"; exit $?` on purpose, so bash never reads a rewritten file past that point.
- `./scripts/deploy.sh passwd <name>` — `docker compose exec api api passwd <name>`: a new random password for that account, printed once, every login of it out. The only reset there is.
- `--prune-deploy`, with any of the first three — first gives the disk back what the builds took, then deploys as asked. `docker builder prune -af` (buildkit's cache: every cargo target dir it ever kept, the usual 10 GB+ on a box that compiled a few times; it is docker's, not this project's, so every project's goes and each comes back on its next build) and `docker image prune -f` (untagged images). It runs before the free-disk check, so the box that failed with "only 2664MB free" passes it on the same command; the check's own error message says to try it. Volumes, containers, tagged images and the swapfile stay (the build needs the swap on a small box). A failed prune is noted, not fatal: the disk check right after it decides. A `--pull --prune-deploy` that finds nothing to redeploy still prunes.
- images (the default, `--images TAG` to pick the tag) — nothing is compiled on this machine. `docker-compose.yml` names every built image `${IMAGES:-}stream-<x>:${TAG:-latest}`; `deploy.sh` exports both so compose resolves them to the registry's names, and writes them to `.env` so a `docker compose up -d` by hand later starts the same images. `IMAGES`: the environment, else `.env`, else `ghcr.io/<owner>/` from the git remote (lowercased; a remote not on github needs `IMAGES` set, or `--build`). `TAG`: the flag, else the environment, else the last commit that touched what the images are built from (`image-paths`; 7 characters; a shallow checkout is refused with the `git fetch --unshallow` to run, since its boundary commit would pass for that), which is the rule the action and `ship.sh` tag with — so a commit that touched none of them (docs, `deploy.sh`, `docker-compose.yml`, the Caddyfile) runs the images of the one before it, and asks the registry for nothing it never built; `ship.sh` prints its tag, which a box at the same tree works out by itself (`-dirty` ones it cannot: `--images` names them). The `TAG` in `.env` is only the record of the last run, never a default: after a pull it would name the old images. `build_one`, the one function every path gets an image through, uses an image already present under that exact name (sent by `./scripts/ship.sh --to`, or pulled before: a tag is a commit) and otherwise `compose pull`s it; `up -d` gets `--no-build`, so a missing tag fails loudly instead of quietly starting an hour of compiling. The failure text tells `manifest unknown` (the action has not pushed that commit yet) from `denied` (a private package) and lists the stream images that are present. On a machine that is not amd64 (an arm laptop) the pull asks for the amd64 variant and docker runs it under emulation, with a note; `--build` makes native ones. The disk floor is 1.5 GB and no swapfile is made: a 1 GB box runs the stack. `--pull` in images mode skips the changed-files detection — the pulled commit's tag is the change — and `up -d` recreates only the containers whose image changed, so a push that touched only the api leaves a live stream up. `--prune-deploy` also removes `stream-*` images of other tags that no container runs.
- `--build`, with any of the first three — compile the images on this machine with `compose build`, as `stream-<x>:latest` whatever `.env` names (`IMAGES` and `TAG` are exported empty for the run; `.env` is left alone). The 4 GB disk floor and the swapfile apply. For a laptop with changes that are not pushed, or a box with no registry. `./scripts/test.sh` and `test/redeploy.js` use it: the tests are about this checkout, not about what the action built.

`.github/workflows/images.yml` is the usual other half: on every push to `main` that touches what the images are built from (`image-paths`, copied into its `paths:` filter by hand, the Caddyfile left out; or by hand, `workflow_dispatch`), four parallel jobs build the images natively on `ubuntu-latest` (x86-64, 4 cores) with the same Dockerfiles, `BUILD=<tag>`, `CARGO_BUILD_JOBS=4`, and push them to `ghcr.io/<owner, lowercased>/stream-<x>:<tag>` and `:latest`, the tag being the last commit that touched those paths (a push can end on a docs commit; `deploy.sh` names the images by the same rule), logging in with the workflow's own `GITHUB_TOKEN` (`permissions: packages: write`), so no personal token exists anywhere. Buildkit's cache lives in the actions cache (`type=gha`, one scope per image, `mode=max`): a source change is a few minutes, a `Cargo.lock` change rebuilds the dependency layers once. The images carry `org.opencontainers.image.source`, which links each package to the repo, and packages a workflow creates take the repo's visibility: public, no step to click. Free for a public repo (minutes and public packages both). On the box, `./scripts/deploy.sh --pull --images` with no tag uses the commit it just pulled, which is the tag the action pushed; running it before the action finished fails on `manifest unknown` with a message that says so.

`ship.sh`, the by-hand half, runs on the laptop. `./scripts/ship.sh --to gcloud:<instance>` (or `--to user@host`, anything `ssh` takes) builds the images for `linux/amd64` (what the cloud boxes are; `PLATFORM=` to change) with the same Dockerfiles and the same `BUILD` rule (`<commit>`, `-dirty` when `api/ video/ frontend/ Cargo.*` have edits), tags them `stream-<x>:<commit>`, and streams them into the box's docker as one `docker save | gzip | ssh … docker load`: layers the images share go once, nothing lands on disk at either end, and no registry or account is involved. It checks first that docker answers on the box. `./scripts/ship.sh` with no `--to` pushes to a registry instead (`IMAGES`, default `ghcr.io/<owner of the git remote>/` lowercased, as `<commit>` and `latest`) for several boxes or ci later; it refuses without a `docker login` to that registry (once: `gh auth refresh -s write:packages,read:packages`, then `gh auth token | docker login ghcr.io -u <you> --password-stdin`), and packages a laptop push creates are private on ghcr until made public once in their settings (unlike the action's). `--local` builds for this machine and keeps them here as `stream-<x>:local`. On an arm laptop the amd64 build runs under rosetta: `rustc` is about 8× slower than native there (the api image took 4 minutes with nothing cached), still far ahead of a small box, and the dependency layers are cached after the first time, so a source change is a minute or two. It prints the deploy command for the box at the end.

Every full or partial run, and a `--pull` that finds nothing to redeploy, also appends to `.env` whatever keys `.env.example` has that `.env` lacks (comment block and default included; `ENV_NAME`, `ADMIN_NAMES`, `OPS_TOKEN`, the `DUMMY_*`), so a pull that brings a new knob leaves it in `.env` to find. Existing lines are never changed, with one exception: an empty or missing `ENV_NAME` is filled in with this machine's hostname (lowercased, `a-z 0-9 -`, 32 chars at most), once.

The images carry `BUILD`, so a commit that touches an image path is a new image for every service even on a full cache hit, and `compose up -d` swaps every container whose image changed: a full deploy restarts `video` whenever the images moved since the last one, and every live stream ends. The script prints the same warning `./scripts/deploy.sh video` does before `up`, and does not stop (a full deploy is "everything"). Partial and `--pull` runs touch only what changed, as before.

Full deploy (builds `pages`, `video`, `dummy`, `api`): pick `PUBLIC_IP` (arg > `$PUBLIC_IP` > existing `.env` unless it is `127.0.0.1` > Linux: ipify, `ip route`, `hostname -I`; macOS: en0/en1 > `127.0.0.1` with a warning; warns when `.env` disagrees with what the machine looks like; on Linux, when the pick is on no local interface and the box has a lan ip, a loud warning names both and the command to switch — right behind cloud 1:1 nat, wrong on a home lan, where ipify answers with the router and video stays black for everyone; the pick stands either way); Linux: install docker + compose plugin if missing, refuse if 80/443 are taken by something else (macOS too, via lsof), refuse under 4 GB free disk (6 GB when the swapfile is about to be made out of it), add a 2G swapfile when RAM < 2GB and there is no swap (session only), `ufw allow 80/tcp 443/tcp 7882/udp` if ufw is active (docker-published ports bypass ufw anyway; the rules keep `ufw status` honest); macOS: refuse if Docker Desktop's credential helper hangs; pick `CARGO_BUILD_JOBS` = `$CARGO_BUILD_JOBS` if set, else RAM / 1.5 GB capped at the core count (the `.env` value is overwritten each run); write `.env`, fill in `ENV_NAME` if empty; `docker compose build pages`, then `video`, `dummy`, `api`, each with `--build-arg BUILD=` (a build failure prints the out-of-memory hint), then `up -d`, then `docker image prune -f` (the untagged images the swap left; the build cache stays, `docker builder prune` is yours); poll `https://<PUBLIC_IP>/api/health` with `curl -k` every 3s for up to 120s, accepting `https://127.0.0.1` after 30s (cloud 1:1 nat; the warning says that on a home lan this means the wan ip is in `.env` and video is black for lan watchers); print the url; write `.deployed`; exit non-zero if nothing answered. Rerunnable. Cloud firewalls: open 80/tcp, 443/tcp, 7882/udp by hand.

## known limits

- One fan-out task per stream: roughly 150–200 watchers per stream on one core, then egress (~300 at 2.5 Mbps on 1 Gbps). That is the "add fanout computers" step, not this test.
- No simulcast or downstream congestion control. A watcher on a bad link gets loss, not a lower quality.
- No rate limiting on the api or the socket, except the login, signup and error-report counters (see "accounts" and `debugging.md`). Anyone can publish an unclaimed name, watch, or set an unclaimed bio, or be `online` as it (`status.md`: a free name's presence is anyone's, like its bio). Session rows grow with every go-live.
- One `/events` socket per browser, open on every page, on the events process: a file descriptor each (`nofile` 65536 on the container), tens of kilobytes each. `GET /online` inside the network says how many. The gateway reads the `live:` key, not video, for `streaming`; video calling `stop` when a publisher leaves is what keeps that honest within ~15s of a crash, and the key is set at go-live, a second or two before video has the publisher, so the word can run that far ahead of the `live` fact (a watcher who asks on the word alone is answered not live and waits for the fact).
- No cpu or memory limits on the containers: small vms vary, and a limit that kills `video` ends every stream at once. `video` and `dummy` carry `pids_limit: 256` (one ffmpeg per live stream, so room for ~25); watch `docker stats` for the rest.
- IPv4 only. UDP-blocked networks cannot watch.

## later, not now

When one machine's outbound bandwidth fills up, run more fanout machines. The streamer node still takes one upload and sends one copy to each fanout machine. Watchers connect to a fanout machine, not to the streamer.

Do not build that split in this test. Do not put transcode on the fanout path. The v1 media process is already "ingest role plus fanout role" so the frontend's api can stay the same when those roles move apart.
